# AI自动化研报/新闻摘要生成平台 — 功能架构设计书

## 1. 项目概述

### 1.1 项目名称

**智览** — AI自动化研报/新闻摘要生成平台

### 1.2 项目定位

面向金融、咨询、媒体行业的智能文本处理平台，基于 **AgenticRAG（代理式检索增强生成）** 架构，实现从多源信息采集、智能去重聚类、深度摘要生成到每日简报推送的全链路自动化。

### 1.3 核心价值

| 维度 | 说明 |
|------|------|
| 效率提升 | 将人工数小时的信息搜集与研报撰写压缩至分钟级 |
| 质量保障 | 结构化研报模板 + LLM深度分析，确保专业性与完整性 |
| 技术深度 | 展示 LangChain 在长文本处理与复杂工作流编排上的能力 |

## 4. 核心功能模块设计

### 4.1 模块一：多源信息采集 (Multi-Source Collector)

#### 功能描述
定时从多个数据源抓取特定主题的新闻、财报、公告等文本信息。

#### 子模块划分

| 子模块 | 说明 |
|--------|------|
| NewsAPI 采集器 | 通过 NewsAPI 获取全球新闻，支持关键词、语言、时间范围过滤 |
| 自定义爬虫 | 针对特定财经网站（如新浪财经、东方财富等）的定向爬取 |
| RSS 订阅 | 支持主流财经媒体的 RSS 源订阅 |
| 财报PDF解析 | 解析上市公司财报PDF，提取关键财务数据 |

#### 数据模型

```python
class RawArticle:
    source: str          # 来源（newsapi / crawler / rss）
    title: str           # 标题
    content: str         # 正文内容
    url: str             # 原文链接
    published_at: datetime  # 发布时间
    author: str          # 作者
    language: str        # 语言
    topic_tags: list[str]   # 主题标签
    raw_html: str        # 原始HTML（备用）
```

#### 关键设计

- **采集频率**：可配置 Cron 表达式，默认每 2 小时采集一次
- **增量采集**：基于 URL 哈希 + Redis 记录，避免重复抓取
- **反爬策略**：User-Agent 轮换、请求间隔控制、代理池支持
- **容错机制**：单源失败不影响整体采集，记录失败日志并重试

---

### 4.2 模块二：去重与聚类 (Deduplication & Clustering)

#### 功能描述
识别相似新闻，合并同类项，将海量碎片化信息聚合为有意义的主题簇。

#### 去重策略（三层）

```
第一层：精确去重
  └── URL哈希 + 标题哈希 → Redis BloomFilter

第二层：近似去重
  └── SimHash / MinHash → 文本指纹相似度 > 0.9 判定为重复

第三层：语义去重
  └── Embedding向量 → 余弦相似度 > 0.92 判定为语义重复
```

#### 聚类算法

| 方法 | 说明 |
|------|------|
| 语义Embedding | 使用 DashScope `text-embedding-v3`（1024 维）将文章向量化 |
| 聚类算法 | HDBSCAN（自动确定簇数量，优于K-Means） |
| 簇合并策略 | 同一簇内按时间排序，选取最早+最权威来源为代表 |
| 簇标签生成 | LLM 自动生成簇的主题标签 |

#### 输出数据结构

```python
class NewsCluster:
    cluster_id: str          # 聚类ID
    topic_label: str         # LLM生成的主题标签
    articles: list[Article]  # 簇内文章列表
    representative: Article  # 代表性文章
    event_timeline: list     # 事件时间线
    importance_score: float  # 重要性评分
```

### 4.3 模块三：AgenticRAG 深度摘要生成

#### 功能描述
不是简单的文本总结，而是生成"背景-现状-趋势-风险"结构化的专业研报摘要。

#### RAG 检索增强流程

```
用户主题/聚类标签
       │
       ▼
┌─────────────────┐
│  Query改写       │  LLM将主题扩展为多个检索Query
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  多路召回        │  ES kNN向量检索 + ES BM25关键词检索 + 时间过滤
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  重排序(Rerank)  │  DashScope qwen3-rerank
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  上下文组装      │  将Top-K文档片段 + 历史背景组装为Prompt
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  结构化生成      │  LLM按研报模板生成深度摘要
└─────────────────┘
```

#### 研报输出模板

```markdown
# [主题标题]

## 一、事件背景
- 事件起因与历史脉络
- 关键参与方与利益关系

## 二、现状分析
- 最新动态与关键数据
- 各方立场与反应
- 市场/行业影响评估

## 三、趋势研判
- 短期趋势预测（1-3个月）
- 中长期趋势展望（6-12个月）
- 关键驱动因素与变量

## 四、风险提示
- 政策/监管风险
- 市场波动风险
- 技术/ operational 风险

## 五、关键数据附录
| 指标 | 数值 | 变化 |
|------|------|------|
| ...  | ...  | ...  |

---
*信息来源：[来源列表]*
*生成时间：[timestamp]*
```

#### 关键设计

- **长文本处理**：自研字符滑动窗口切分器（chunk_size=500, overlap=100，标题作前缀）
- **多轮推理**：对于复杂主题，Agent 可自主决定是否需要多轮检索补充信息
- **引用溯源**：每个论点标注信息来源，支持点击跳转原文

## 5. LangGraph Agent 详细设计

### 5.1 Agent 角色定义

| Agent | 职责 | 工具集 |
|-------|------|--------|
| **CollectorAgent** | 多源数据采集 | NewsAPI, WebScraper, RSSReader |
| **PreprocessAgent** | 文本清洗与标准化 | HTMLCleaner, LanguageDetector |
| **DedupAgent** | 去重检测 | BloomFilter, SimHash, EmbeddingSimilarity |
| **ClusterAgent** | 语义聚类 | HDBSCAN, EmbeddingModel |
| **ResearchAgent** | RAG检索增强 + 深度摘要 | VectorStore, Reranker, LLM |
| **ReviewAgent** | 质量审核 | FactChecker, HallucinationDetector |
| **ComposeAgent** | 研报组装 | ReportTemplate, MarkdownRenderer |
| **ExportAgent** | 格式导出 | PDFGenerator, MarkdownWriter |
| **DispatchAgent** | 推送分发 | APIExporter, FileExporter |

### 5.2 LangGraph 状态定义

```python
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph

class PlatformState(TypedDict):
    # 输入
    topics: list[str]               # 监控主题列表
    date_range: tuple[str, str]     # 时间范围

    # 采集阶段
    raw_articles: list[dict]        # 原始文章
    collection_errors: list[str]    # 采集错误

    # 预处理阶段
    cleaned_articles: list[dict]    # 清洗后文章
    duplicates_removed: int         # 去重数量

    # 聚类阶段
    clusters: list[dict]            # 聚类结果
    cluster_labels: list[str]       # 聚类标签

    # 摘要阶段
    research_reports: list[dict]    # 深度研报
    rag_context: list[dict]         # RAG检索上下文

    # 审核阶段
    review_passed: bool             # 审核是否通过
    review_feedback: list[str]      # 审核反馈

    # 输出阶段
    daily_brief: str                # 日报Markdown内容
    pdf_path: str                   # PDF文件路径
    dispatch_status: dict           # 推送状态
```

### 5.3 条件边与循环逻辑

```python
# 审核不通过 → 重新生成（最多3次）
def review_router(state: PlatformState) -> str:
    if state["review_passed"]:
        return "compose"
    if retry_count >= 3:
        return "compose"  # 强制通过，附带审核意见
    return "research"     # 返回重新生成

# 采集失败 → 降级处理
def collection_router(state: PlatformState) -> str:
    if len(state["raw_articles"]) == 0:
        return "fallback_cache"  # 使用Redis缓存的昨日数据
    return "preprocess"
```

## 6. 缓存策略设计 (Redis)

### 6.1 缓存层级

| 缓存类型 | Key格式 | TTL | 说明 |
|----------|---------|-----|------|
| API响应缓存 | `api:{endpoint}:{params_hash}` | 30min | NewsAPI等外部API响应 |
| 文章去重缓存 | `seen:{url_hash}` | 7d | 已处理文章的URL指纹 |
| Embedding缓存 | `emb:{content_hash}` | 30d | 文本向量，避免重复计算 |
| 聚类结果缓存 | `cluster:{date}:{topic}` | 24h | 当日聚类结果 |
| 研报缓存 | `report:{date}:{cluster_id}` | 7d | 已生成的研报 |
| 日报缓存 | `brief:{date}` | 30d | 历史日报 |

### 6.2 降级策略

```
请求 → 查Redis缓存
  ├── Hit → 直接返回
  └── Miss → 调用实际服务
              ├── 成功 → 写入缓存 + 返回
              └── 失败 → 返回降级数据（过期缓存/默认值）
```

### 7.2 数据流全景

```
外部数据源 (NewsAPI / 爬虫 / RSS / 财报PDF)
    │
    ▼
[采集Agent] → raw_articles → Redis(去重+缓存)
    │
    ▼
[预处理Agent] → cleaned_articles (清洗/分段/语言检测)
    │
    ▼
[去重Agent] → 过滤重复 → BloomFilter + SimHash + Embedding
    │
    ▼
[聚类Agent] → news_clusters → Elasticsearch(向量+关键词索引)
    │
    ▼
[RAG检索] → 相关上下文片段 → LLM增强检索
    │
    ▼
[摘要Agent] → research_reports (结构化深度研报)
    │
    ▼
[审核Agent] → 质量检查 (事实核查 + 幻觉检测)
    │         ├── 通过 → 下一步
    │         └── 不通过 → 返回摘要Agent重新生成
    ▼
[组装Agent] → daily_brief (Markdown格式日报)
    │
    ▼
[导出Agent] → PDF / Markdown 文件
    │
    ▼
[推送Agent] → API / 文件下载
```

## 9. 关键技术难点与解决方案

### 9.1 长文本处理

| 挑战 | 解决方案 |
|------|----------|
| 单篇新闻超长 | RecursiveCharacterTextSplitter 智能分段 |
| 多文档上下文窗口超限 | Map-Reduce 摘要策略：先分篇摘要，再合并提炼 |
| 研报生成需要大量上下文 | RAG分层检索 + Reranker 精选Top-K最相关片段 |

### 9.2 摘要质量保障

| 挑战 | 解决方案 |
|------|----------|
| LLM 幻觉 | ReviewAgent 事实核查 + 引用溯源 |
| 内容空洞 | 强制要求数据引用 + 结构化模板约束 |
| 观点偏颇 | 多源交叉验证 + 平衡性检查Prompt |

### 9.3 工作流可靠性

| 挑战 | 解决方案 |
|------|----------|
| Agent 执行失败 | LangGraph Checkpointing + 断点恢复 |
| 外部API不稳定 | Redis缓存降级 + 指数退避重试 |
| 处理时间过长 | 异步执行 + 进度回调 + 超时控制 |

## 11. RAG 检索增强实施成果（六阶段）

> 本章记录 AgenticRAG 检索链路从设计到落地的六阶段实施成果。
> 代码位于 `backend/app/rag/`，评估脚本位于 `backend/` 根目录。

### 11.1 六阶段总览

| 阶段 | 内容 | 核心实现 | 文件 |
|------|------|----------|------|
| 一 | 文档切分 | 字符滑动窗口 chunk_size=500 / overlap=100，标题作前缀 | `app/rag/chunker.py` |
| 二 | 向量索引 | ES dense_vector（1024 维，index:true）+ DashScope text-embedding-v3 | `app/rag/indexer.py` |
| 三 | 混合检索 | BM25（multi_match）+ kNN 双路召回 + RRF 融合（k=60） | `app/rag/retriever.py` |
| 四 | 重排 | DashScope qwen3-rerank，失败降级为原始排序 | `app/rag/retriever.py` |
| 五 | QA 生成 | DeepSeek deepseek-chat，带 [编号] 引用溯源，信息不足时诚实说明 | `app/rag/qa.py` + `app/api/qa.py` |
| 六 | 评估 | 人工 query 集 + 负样本，Recall / MRR / 误报率 | `eval_human_queries.py` / `eval_absent.py` |

### 11.2 各阶段要点

**阶段一 · 文档切分**
- 中文按字符切分，`chunk_size=500`、`overlap=100`，滑动窗口保证跨段上下文连贯
- 每个 chunk 携带文章标题前缀（`标题\n正文片段`），检索命中自带语义上下文

**阶段二 · 向量索引**
- ES `news_chunks` 索引，`embedding` 字段为 `dense_vector(1024, index=true, similarity=cosine)`
- 向量由 DashScope `text-embedding-v3` 生成，`bulk` 批量写入
- `index_pending_articles()` 增量索引 `dedup_status=unique 且 indexed=false` 的文章

**阶段三 · 混合检索**
- BM25 路：`multi_match` 检索 `title^3 / text^2 / content`
- kNN 路：`dense_vector` 语义检索
- RRF（Reciprocal Rank Fusion，k=60）融合两路排名，双路命中者得分更高
- 单路失败自动降级为另一路，均失败返回空

**阶段四 · 重排**
- 召回 `top_k*2` 候选，调用 DashScope `qwen3-rerank` 精排取 `top_k`
- 调用失败时降级为 RRF 原始排序，保证可用性

**阶段五 · QA 生成**
- 将 top-k 片段编号组装为上下文，DeepSeek 严格依据片段作答
- 引用处标注 `[编号]`，片段不足时明确说明「信息不足」，防止幻觉

**阶段六 · 评估**
- 指标：文章粒度 Recall@5/@10、MRR（文章粒度）、负样本 top-1 相似度（误报检测）

### 11.3 评估结果（数据扩充后）

**数据规模**：677 篇文章 / 841 个 chunk（含 11 篇 13-chunk 的 BBC 全文长文，其余多为单 chunk 摘要）。

**正样本（28 条人工口语化 query：13 长文 + 10 短文 + 5 同主题混淆对）**

| 配置 | Recall@5 | Recall@10 | MRR |
|------|----------|-----------|-----|
| BM25 | 1.000 | 1.000 | 0.941 |
| RRF 混合 | 1.000 | 1.000 | 1.000 |
| RRF+Rerank | 1.000 | 1.000 | 1.000 |

**负样本（10 条库中不存在主题，avg top-1 余弦相似度，越低越克制）**

| 配置 | avg top-1 相似度 |
|------|------------------|
| BM25 | 0.405 |
| RRF 混合 | 0.469 |
| RRF+Rerank | 0.469 |

### 11.4 评估结论

1. **Recall 饱和是真实现象**：677 篇小语料下，新闻标题高度特化、关键词唯一，三种配置 Recall@5/@10 均达 1.0，无法用 Recall 区分。
2. **MRR 体现排序增益**：BM25 有 3/28 条未排第一（伊朗高层信号、贾鲁河溃口、日本军国主义），RRF 混合召回全部纠正，Rerank 保持，验证了混合召回 + 重排的排序价值。
3. **负样本暴露向量检索特性**：BM25 对领域外 query 最克制（0.405），kNN 引入后 top-1 相似度略升（0.469），但仍低于 0.5 安全阈值，说明系统整体不误报；向量检索对「表面语义相近」的不相关主题（如「苹果手机」→「高原苹果」）存在轻微误报倾向。
4. **数据瓶颈**：旧数据为 RSS 摘要（平均 102 字符），单篇仅 1 chunk；BBC 中文源为全文 HTML（4700+ 字符），单篇可切 13 chunk，是扩充检索语料的主要来源。
